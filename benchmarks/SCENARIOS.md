# Benchmark scenarios

Canonical list of what each numbered scenario measures.  Individual `bench_*.cpp` files should reference a scenario by number ("implements Scenario 3") rather than re-describing what it tests - this file is the single source of truth for that, generated from `compare.py`'s `SCENARIO_GROUPS`.  If a scenario's definition changes, update it here first.

| # | Name | What it tests | Canonical benchmark(s) |
|---|---|---|---|
| 1 | Single-threaded emission, 1 connection | The cheapest possible operation: one synchronous `trigger()`/`emit()` to exactly one connected handler, no threading, no contention. The floor every other scenario builds on. | `BM_Emit_1Connection` |
| 2 | Single-threaded emission, N connections | Same as 1, but N handlers on one event, N = 1/10/100/1000 - how dispatch cost scales with connection-list size alone. | `BM_Emit_NConnections/{1,10,100,1000}` |
| 2a | Single-threaded emission, 1 Auto connection | Implemented by Pulsar and Qt6, the two libraries with an auto-resolving connection type. Identical to 1, but connecting via `ConnectionType::Auto`/`Qt::AutoConnection` instead of an explicit direct type - confirms Auto resolves to zero-overhead direct dispatch when sender and receiver share no distinct thread context. vdk-signals has an analogous auto-resolving `exec{}` default but no dedicated benchmark for it in this suite. | `BM_Emit_1Connection_Auto` |
| 2b | Single-threaded emission, N Auto connections | The N-connection version of 2a, same N as Scenario 2. | `BM_Emit_NConnections_Auto/{1,10,100,1000}` |
| 2c | Single-threaded emission, 1 connection, syntax comparison | Whether connection *syntax* has hidden runtime cost, holding everything else fixed: compile-time template member-function vs. runtime free-function pointer vs. compile-time free-function vs. directly-owned lambda. | `BM_Emit_1Connection`, `BM_Emit_1Connection_Free`, `BM_Emit_1Connection_FreeNTTP`, `BM_Emit_1Connection_Lambda` |
| 2d | Single-threaded emission, N connections, syntax comparison | The member-function counterpart to 2c: compile-time NTTP member-connect vs. a runtime member-pointer argument, at N = 1/10/100/1000. | `BM_Emit_NConnections/{N}`, `BM_Emit_NConnections_RuntimeMethod/{N}` |
| 3 | Connect / disconnect throughput | Repeated connect-then-disconnect in a loop - isolates connection-list bookkeeping cost from dispatch cost (no `trigger()`/`emit()` calls). | `BM_ConnectDisconnect` |
| 4 | Scoped receiver lifetime | A receiver's connections torn down automatically on destruction (RAII), not via explicit `disconnect()`. | `BM_ScopedReceiverLifetime` |
| 5 | Cross-thread deferred emission | One thread emits; a second thread (the receiver's actual owning context) later drains and executes the handler. Measures the full round trip - queue, wake, dequeue, invoke. Only libraries with a native deferred-dispatch primitive can appear here. | `BM_CrossThreadDeferred[_ConcurrentEvent]` |
| 6 | Thread-affinity forwarding | Forcing dispatch back onto the *sender's* own thread, not the receiver's. Pulsar has a native primitive (`BasicEvent::operator()`'s sender-loop check); other libraries need a workaround, benchmarked separately. | `BM_SenderDeferral_ThreadAffinity/{1,5}`, `BM_ThreadAffinityForwarding_*` |
| 7a (receiver-deferred) | Genuine cross-thread queue + drain, receiver's context | One or more emitter threads post; the receiver's owning thread drains and executes. Only libraries with a deferred-dispatch primitive at all appear here. | `BM_ConcurrentEmission_PerReceiver[_ConcurrentEvent]/{1,5}` |
| 7a (execute-now, serialised) | Forced one-handler-at-a-time dispatch | Synchronous dispatch, externally forced to serial. The fair cross-library point - libraries that only serialize internally, libraries that need an added external mutex, and libraries with a native serialized type all land here on equal footing. | `BM_ConcurrentEmission_Direct_Serialized[_Event]/{1,5}` |
| 7a (execute-now, parallel) | Synchronous dispatch, no external serialisation | Handler invocations from different threads may genuinely run concurrently. Only libraries whose own policy can actually run unserialized appear here. | `BM_ConcurrentEmission_Direct_Parallel[_Event]/{1,5}` |
| 7b | Concurrent emission, serialised dispatch, multiple mechanisms | Multiple threads emitting concurrently, all serialised onto one shared drain/dispatch context - compares several real-world patterns for achieving this, not just one. | `BM_ReceiverDeferral_Serialised/{1,5}`, `BM_ConcurrentEmission_Serialised_*` |
| 8a | Disconnect-by-target, linear scan | Pulsar-only. Disconnecting a specific target via linear scan of the connection list. Does not exercise batch/GenData mechanics - see 8b. | `BM_DisconnectByTarget_LinearScan/{1,10,100,1000}` |
| 8b | Bulk disconnect via tracked-connection batch | Disconnecting all of a receiver's connections in one batched call, as an alternative to 8a's per-target scan. | `BM_DisconnectTracker_Batch/{1,10,100,1000}` |
| 9 | Contention scaling | How each library's thread-safety mechanism scales as concurrent contention increases, isolated from every other variable: a fixed receiver count, only thread count varies (1 → 32), no external serialisation added by the benchmark. | `BM_ContentionScaling_Direct[_Event]/{1,2,4,8,16,32}` |

For the full description of any scenario (including per-library column mapping and any library-specific caveats), see the corresponding entry in `compare.py`'s `SCENARIO_GROUPS`, or the generated `BENCHMARK_RESULTS.md`.
